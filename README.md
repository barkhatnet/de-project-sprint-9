# Выполнение:  

## Задача 0
Проверка готовности шаблонов  
## Реализация 0  
Проверяем шаблоны репозитория с заготовками для двух новых сервисов. Шаблоны идентичные, поэтому неважно, для какого сервиса можно использовать. Как и в случае с первым сервисом, цель этих заготовок — избавиться от рутинных действий и позволить сконцентрироваться на создании микросервиса. 

В полученные шаблоны новых сервисов добавляем первый сервис работы с STG слоем данных, который был разработан ранее. В результате получаем следующую структуру сервисов:
- solution / `service_stg` (первый сервис)
- solution / `service_dds` (второй сервис)
- solution / `service_cdm` (третий сервис)

## Задача 1  
Создание второго сервиса: распланировать работу над сервисом  
## Реализация 1  
Второй сервис является частью общей системы, которую спроектировали ранее. Задача этого сервиса —  заполнять данными детальный слой DWH в Postgres. На вход он получает выходные данные из первого сервиса.

Продумать логику работы над сервисом:
Нужно посмотреть требования первого сервиса и сформулировать DoD сервиса: что и как должен делать сервис; какие данные, в каком виде и как выдавать.

Первый сервис был реализовал для записи в слой STG. Для реализации сервиса работы данного сервиса создавался топик в "Yandex Cloud / Managed Service for Kafka"

**KAFKA_STG_SERVICE_ORDERS_TOPIC**

Продумать логику работы сервиса:
Записать входную точку сервиса: какие данные и как приходят.
Продумать путь между входной и выходной точками сервиса: какие операции нужно провести над данными и артефактами (схемами, таблицами, топиками), чтобы перейти из точки А в точку Б.

Для реализации логики работы второго сервиса создаем схему работы двух сервисов:

**1. STG [KAFKA_SOURCE_TOPIC] > [KAFKA_STG_SERVICE_ORDERS_TOPIC]**  
**2. DDS [KAFKA_STG_SERVICE_ORDERS_TOPIC] > [KAFKA_DDS_SERVICE_ORDERS_TOPIC]**  

Нужно оценить, какой код нужно написать, чтобы реализовать нужные преобразования.

Определить общий список задач: подумать, что уже готово, а что ещё нужно получить и сделать — файлы, шаблоны, схемы, доступы.

На основе проделанного ранее составить план действий по реализации сервиса.

## Задача 3  
Создание второго сервиса: зарелизить сервис в Kubernetes  
## Реализация 3  
Теперь предстоит зарелизить сервис в Kubernetes.

`docker build . -t cr.yandex/crppueq1vkg674o7mk6h/dds_service:v2026-03-23-r1`  
`docker push cr.yandex/crppueq1vkg674o7mk6h/dds_service:v2026-03-23-r1`  
по аналогии с ранее развернутым сервисом STG  
`docker build . -t cr.yandex/crppueq1vkg674o7mk6h/stg_service:v2026-03-23-r1`  
`docker push cr.yandex/crppueq1vkg674o7mk6h/stg_service:v2026-03-23-r1`  

Развернем образ в Kubernetes.  
`helm upgrade --install --atomic dds-service app -n st-k8s2512130d47f9`    
по аналогии с ранее развернутым сервисом STG  
`helm upgrade --install --atomic stg-service app -n st-k8s2512130d47f9`  

Проверим с помощью kubectl, что сервис поднялся.  
`kubectl get pods -n st-k8s2512130d47f9`  

Подключаемся к Postgres SQL и убедимся, что таблицы заполняются данными.

## Задача 7  
Создать дашборд в DataLens
## Реализация 7  
Выполняем последовательно действия:
1. Подключаем к DataLens хранилище.
2. В DataLens создаем датасет для построения графиков на основе слоя витрин из хранилища.
3. Создаем дашборд, который будет включать в себя такие графики:
- круговая диаграмма, показывающая популярность категорий блюд на основе доли пользователей, которые заказывали блюда этой категории;
- круговая диаграмма, показывающая популярность категорий блюд на основе доли заказов, в которых были блюда этой категории;
- столбчатая диаграмма, показывающая популярность блюд по количеству уникальных пользователей, заказавших блюдо;
- столбчатая диаграмма, показывающая популярность блюд по количеству заказов, в которых было блюдо.
